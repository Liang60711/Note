# 核心組件

## Master Node 組件

1. 如果要做 HA ， Master 節點數建議為 3,5,7,9 (大於1的奇數)，因為 RAFT 選舉演算法。

2. ETCD 用來存儲當前
    
    - 集群配置資訊、參數。

3. Api server 

    - 跟工作節點的溝通，都是通過此組件，溝通方式使用 HTTP RESTful 的方式。

    - Kubectl 下的指令，也是會發給 api server 審核權限。

4. Scheduler 

    - 分配 Pod 要放到哪一個 Node 跑。

    - 不負責建立 Pod，只是負責將未指定節點的 Pod，計算後發出指令。

    - 工作 Node 的狀態會由 Kubelet 回報給 API Server，API Server 再把狀態持久化到 etcd；Scheduler 透過 API Server 取得這些資訊，而不是直接讀 etcd。

5. Controller Manager

    - 集群裡的自動化控制中心，負責監督集群狀態並讓`實際狀態`跟隨`想達到的目標狀態`。
    
    - 實際上建立 Pod 的步驟

        ```
        使用者
        ↓
        Deployment (配置: 3個Pod)
        ↓
        Controller Manager
        ↓
        建立 Pod 物件，紀錄在 ETCD
        ↓
        Scheduler，發現 ETCD 有未綁定的 Pod 物件
        ↓
        指定 Node，並將 Pod 與該節點綁定，回存給 ETCD
        ↓
        Kubelet
        ↓
        Container Runtime
        ↓
        真正建立 Container
        ↓
        程式跑起來
        ```

## Work Node 組件

1. kubelet

    - 存在於 work node 中的窗口，負責對接 master node。

    - 監聽 master node 的 api server 有沒有發送建立 Pod 的任務。

    - 調用 work node 的 CRI (容器運行時接口，Container Runtime Interface)。


2. kube proxy

    - 負責把 Kubernetes Service 的網路流量，轉發到對應的 Pod。

    - 也去監聽 api server，防火牆規則、負載均衡規則。

3. container runtime

    - 負責拉取 Container Image、建立、啟動、停止與刪除容器。

    - 常見的 Container Runtime 包含 containerd、CRI-O 和 Docker Engine。


| 元件                    | 是不是 Pod？  | 實際在哪裡                          |
| --------------------- | --------- | ------------------------------ |
| **kube-proxy**        | ✅ 通常是 Pod | 通常由 DaemonSet 跑在每個 Node        |
| **kubelet**           | ❌ 不是 Pod  | 直接跑在 Node 的 OS 上|
| **Container Runtime** | ❌ 不是 Pod  | 直接跑在 Node 的 OS 上|
